# Claude Code's built-in sandbox (with information-guard)

Claude Code has its own sandbox — `sandbox-exec` wrapping the Bash tool, plus permission deny rules. For Claude, **use the built-in sandbox instead of wrapping it with `information-guard-sandbox`.** This is the same approach as Codex: the agent has its own sandbox, so don't nest a process-level wrapper around it.

This doc explains why you'd be tempted to wrap Claude anyway, why that breaks, and how the native sandbox + deny rules closes most of the same gaps without the breakage.

## Claude's sandbox model

Claude Code has two protection mechanisms, both off by default:

1. **Permission rules** (`allow` / `ask` / `deny` in `settings.json`) — pattern matching on tool invocations. `Read(**/secrets/**)` blocks the Read tool from matching paths. Enforced in Claude's process, at the point a tool is invoked.
2. **The sandbox** (`sandbox.enabled` in `settings.json`, or the `/sandbox` command) — `sandbox-exec` wrapping the **Bash tool only**. Kernel-level read/write containment on commands the Bash tool runs.

The main Claude process (auth, keychain, the Read/Edit/Write tools themselves, MCP servers, hooks) is **not** sandboxed by either mechanism.

## Why you'd want to wrap Claude

The native model has real gaps. These are what made a whole-process wrapper like `information-guard-sandbox` appealing:

- **Read/Edit/Write tools are unsandboxed.** Only the Bash tool gets `sandbox-exec`. A `deny` rule on Read is enforced by the permission layer, not the kernel — and only when the Read _tool_ is invoked.
- **Permission rules are bypassable via Bash.** `Read(**/secrets/**)` stops the Read tool, but `python3 -c "open('secret').read()"` via Bash reads the file anyway. (This gap closes once the sandbox is enabled — see below — but it's not obvious, and the sandbox is off by default.)
- **MCP servers bypass both layers.** An MCP server runs in the main process and reads files directly — not gated by permission rules or the sandbox.
- **The config surface is large and subtle.** `allowWrite` / `denyRead` / `denyWrite` / `allowRead` / `additionalDirectories` / `ask`-`allow`-`deny` rules / their interaction with the sandbox. Easy to get wrong.

A whole-process wrapper solves all of this at once: `sandbox-exec` around the entire Claude process means Read/Edit/Write/MCP/hooks all get kernel-level `EPERM` on protected paths. One config, kernel-enforced, no tool-layer gaps.

## Why wrapping breaks

`information-guard-sandbox` wraps the **whole process** — including the main Claude process. Two things break:

1. **Keychain writes are blocked.** The main process (auth, token refresh) is sandboxed, so writes to `~/Library/Keychains/login.keychain-db` are denied by write containment. Claude's credential store falls back to a file but still reads from keychain — which holds a stale token. OAuth token refresh can't persist, so auth fails on the next read.
2. **Setuid binaries can't exec.** macOS Seatbelt denies exec of setuid binaries inside any `sandbox-exec` container. `/bin/ps` is setuid root, so any tool that shells out to `ps` fails with `Operation not permitted`.

The native sandbox avoids both: it only wraps the **Bash tool**, so the main process (auth, keychain) runs unsandboxed. Keychain writes work. Setuid binaries run.

## The resolution: native sandbox + deny rules

Most of the gaps that motivated wrapping actually close once you enable the sandbox and add deny rules from the same `sandbox.json`:

- **The Bash bypass closes.** With the sandbox on, Claude **merges `Read(...)` deny rules into the Bash sandbox profile** as kernel-level `deny file-read-data` rules. So `python3 -c "open('secret').read()"` gets `EPERM` — the permission rule is enforced at the kernel for Bash too. One rule, two layers.
- **Read/Edit/Write tools are gated by the deny rules** at the permission layer (not the kernel, but still enforced).
- **Deny rules fire even in `--dangerously-skip-permissions` mode** — bypass mode skips `allow`/`ask` prompts, but `deny` rules always apply. So you can run Claude in bypass mode and your protected paths stay blocked.

The one gap that remains: **MCP servers** still bypass both layers (they run in the main process, reading files directly). If you need MCP-resistance, that's the one case where the wrapper is the only option — and you accept the keychain/setuid breakage.

## Setup

`information-guard-sandbox --print-claude-config` emits the deny rules + sandbox config from your `sandbox.json` — the same single source of truth used by the process wrapper and Codex. Paste the output into `~/.claude/settings.json`:

```bash
information-guard-sandbox --print-claude-config
```

```jsonc
// Generated by information-guard from ~/.config/information-guard/sandbox.json
// Paste into ~/.claude/settings.json (merge into permissions.deny + sandbox).
{
  "permissions": {
    "deny": [
      "Read(~/agents/pi/agent/memory/**)", // ← protectedPaths
      "Edit(~/agents/pi/agent/memory/**)",
      // ... (Read+Edit for each protectedPath)
      "Read(~/.ssh/**)", // ← READ_PROTECTED_CREDENTIALS
      "Edit(~/.ssh/**)",
      // ... (Read+Edit for each credential path)
      "Edit(~/.zshrc)", // ← WRITE_PROTECTED_DOTFILES
      "Edit(~/.local/bin/**)",
      // ... (Edit only for each sensitive dotfile)
    ],
  },
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": ["~/projects"],
    },
  },
}
```

With `sandbox.enabled: true`, the sandbox is on every launch — no wrapper, alias, or `/sandbox` command needed. Run `claude` normally.

Re-run `--print-claude-config` after changing `protectedPaths` or `writeContainment` in `sandbox.json`.

### What gets emitted

| `sandbox.json` key            | Claude rule                     | Scope                                                                                               |
| ----------------------------- | ------------------------------- | --------------------------------------------------------------------------------------------------- |
| `protectedPaths`              | `Read(...)` + `Edit(...)` deny  | Read + write protected                                                                              |
| `READ_PROTECTED_CREDENTIALS`  | `Read(...)` + `Edit(...)` deny  | Read + write protected (the LLM should never read raw credentials)                                  |
| `WRITE_PROTECTED_DOTFILES`    | `Edit(...)` deny only           | Write-protected, reads allowed (agents can still exec tools in `~/.local/bin`, read `~/.gitconfig`) |
| `writeContainment.allowWrite` | `sandbox.filesystem.allowWrite` | Bash write containment (deny all writes except these)                                               |

For read-protection on a sensitive dotfile, add it to `protectedPaths` in `sandbox.json` (not just `WRITE_PROTECTED_DOTFILES`).

## Tradeoffs vs. the process wrapper

|                           | Native sandbox + deny rules                 | `information-guard-sandbox` wrapper |
| ------------------------- | ------------------------------------------- | ----------------------------------- |
| **Bash writes**           | Kernel-level (sandbox-exec)                 | Kernel-level (sandbox-exec)         |
| **Bash reads**            | Kernel-level (merged from Read deny rules)  | Kernel-level                        |
| **Read/Edit/Write tools** | Permission layer (bypassable via MCP tools) | Kernel-level (EPERM)                |
| **MCP servers**           | Not gated (run in main process)             | Kernel-level (EPERM)                |
| **Keychain**              | ✅ Works (main process unsandboxed)         | ❌ Broken (write blocked)           |
| **Setuid binaries**       | ✅ Works (main process unsandboxed)         | ❌ Broken (exec denied)             |
| **Network**               | Untouched                                   | Untouched                           |

The native approach is softer: Read/Edit/Write tool calls and MCP servers are gated by the permission layer (or not at all), not the kernel. The wrapper gives kernel-level everywhere but breaks keychain and setuid. Use the wrapper only if MCP-resistance is a hard requirement.

## Gotchas

Things that aren't obvious from the settings schema:

- **Use `Edit(...)`, not `Write(...)`, for file deny rules.** Claude only accepts `Edit(path)` for file-permission deny rules; `Write(...)` is ignored with a validation warning.
- **`Read(...)` deny rules merge into the Bash sandbox.** This is what closes the Bash bypass — a `Read(~/.ssh/**)` rule also produces a kernel-level `deny file-read-data` in the Bash sandbox profile. One rule, two layers.
- **`**`globs are workspace-relative;`~/`is absolute.**`Read(**/.env)`only matches within the launch directory's project tree.`Read(~/.ssh/**)`matches everywhere.`--print-claude-config`only emits`~/`-prefixed rules (from `protectedPaths` / credentials / dotfiles), so they apply regardless of launch directory.
- **`additionalDirectories` expands access, not deny-rule scope.** Adding `~` lets the Read tool access all of home, but it does not widen `**`-glob deny rules to cover home. It does widen the Bash sandbox's write surface, though — `allowWrite` is what controls Bash writes, not `additionalDirectories`.
- **Deny rules fire in `--dangerously-skip-permissions` mode.** Bypass mode skips `allow`/`ask` prompts; `deny` rules always apply, and the sandbox stays on. So a bypass-mode Claude still can't read protected paths.
- **`sandbox.enabled: true` auto-enables every launch.** No need for the interactive `/sandbox` command — it's on by default from settings. The command is only for toggling mid-session.
